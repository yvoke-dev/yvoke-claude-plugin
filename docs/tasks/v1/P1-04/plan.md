## What it does

`node scripts/generate-skills.mjs` reads the server's playbook catalogue and writes one
`plugins/yvoke/skills/<name>/SKILL.md` per playbook a user can pick. Each file is a **live stub** (D-04): it
holds the playbook's name, title and description, never its text, and tells Claude to fetch the base
instructions and the playbook from the server before answering. P1-05 runs it on a schedule; P8-01 checks on
claude.ai that Claude really makes the two calls.

A generated stub for `oim-full` would read:

```markdown
---
name: oim-full
description: "Yvoke playbook (OIM): Single-agent full search across the entire One Identity Manager …"
disable-model-invocation: true
---

<!-- Generated by scripts/generate-skills.mjs from the Yvoke server. Do not edit; rerun the script. -->

# OIM Full Search

This is the Yvoke playbook `oim-full` in the area OIM. Its instructions are kept on the Yvoke server, not
in this file. Before you answer anything:

1. Call the Yvoke connector's `get_system_prompt` tool with `name` set to `oim-field-web`. Its text is
   your base instructions.
2. Call the Yvoke connector's `get_playbook` tool with `name` set to `oim-full`, and follow the `text` it
   returns. Where the two disagree, the playbook wins.
3. If either call fails or returns a line starting with `ERROR:`, tell the user the Yvoke server could
   not be reached and stop. Do not answer from general knowledge.
```

### Rules

- **Source: the `list_playbooks` and `list_areas` tools, not MCP `prompts/list`.** The tools are what the
  mod reads in Claude Code (D-11) and what the stub itself calls, and they carry `area` and the playbook's
  own `systemPrompt`. This changes the task entry in [plan.md](../plan.md), which said `prompts/list` with
  `_meta`; the entry is updated in this pull request. The desktop's `_meta` regression becomes its
  equivalent here: a fixture copied from a live `list_playbooks` response pins where each field is read
  from, and a field of the wrong type is ignored rather than passed on.
- **Which playbooks.** Left out: `targetAgent` `orchestrator` or `reviewer` (the server already leaves them
  out; the generator checks again), and `prototype: true` (13 of today's 29 are prototypes, the
  `-browsing` ones). Nothing else is filtered: every area's playbooks are generated (D-15, no single area).
- **Which base instructions** the stub names, worked out when the stub is generated, by the rule P1-07 uses
  (PR #20): the playbook's own `systemPrompt` when **any** area lists it in `systemPrompts`; else its
  area's `defaultSystemPrompt`, passed as `area`; else no argument (the server's active default). Only the
  name is baked in; the text is always fetched live.
- **Name.** The skill name is the playbook name. A name that is not a valid skill name (lowercase letters,
  digits and single hyphens, at most 64 characters), or that two playbooks share, stops the run with an
  error naming the playbooks, and nothing is written.
- **Description.** `Yvoke playbook (<area>): ` followed by the server's description, with line breaks
  collapsed, `<` and `>` replaced by `(` and `)` (claude.ai refuses angle brackets in skill frontmatter),
  and cut at a word boundary to the Agent Skills limit of 1,024 characters, ending in `…`. Most of
  today's descriptions are longer than that. Written as a JSON-quoted string, which YAML reads as is.
- **`disable-model-invocation: true`** on every stub, so the model never starts a playbook in Claude Code
  (D-11) and the 16 stubs do not crowd every coding session's skill list; P1-08 relies on it. Whether Chat
  and Cowork accept this Claude Code field is open (P8-01 lists only portable fields); spike P0-08 checks
  it, and the risk below covers what happens if not.
- **Stable diff.** Stubs are written in name order, with no timestamps, no playbook `version` (it changes
  with every playbook edit while the stub stays the same) and no tool lists. A second run with the same
  catalogue changes nothing. A playbook that left the catalogue loses its folder: the generator owns
  `plugins/yvoke/skills/` and removes any folder it did not write. It prints one line per added, changed
  and removed stub.
- **Reaching the server.** `--url <mcp endpoint>` (default `http://localhost:8080/mcp`), with
  `--dev-mode` for a local yvoke-web in mock mode (the `X-Yvoke-Dev-Mode` header from P0-11) or a bearer
  token from the `YVOKE_TOKEN` environment variable. It speaks MCP over HTTP with `fetch` (initialize, then
  two `tools/call`), so the repository gains no dependency. `--from <file>` reads a saved
  `{ "playbooks": [...], "areas": [...] }` instead. Which credential the scheduled job uses is P1-05's
  question. The token is never printed.
- **Fails closed.** An `ERROR:` answer, an empty playbook list or a server that is down stops the run and
  leaves `skills/` as it was, so a broken server can never delete every stub.

## Order of work

Each step starts with its tests, run red first.

1. **Read the catalogue.** Tests from the live fixture: every field read from where `list_playbooks` puts
   it; wrong types ignored (`tools: "search_corpus"`, `prototype: "true"`, `targetAgent: 7`); a missing
   `area` or `systemPrompt` is `null`, not `""`. Ported from `promptMapping.test.ts`.
2. **Choose playbooks.** Specialists and unlabelled playbooks kept; orchestrator, reviewer and prototype
   left out; two areas both generated. Ported from `playbooks.test.ts` (the rows that apply without
   profiles: the control pair is filtered by role, since this server sends one).
3. **Resolve base instructions.** Own prompt listed in this area; listed only in another area (still used,
   as `findChatPrompt` looks globally); not a chat prompt anywhere (falls to the area default); no area
   default (no argument); blank or padded names.
4. **Render a stub.** Exact text for one fixture playbook (a golden string in the test); description cut at
   1,024 characters on a word boundary; angle brackets replaced; quotes and backslashes survive a YAML
   round trip (checked by reading the frontmatter back); invalid and duplicate names refused.
5. **Write the folder.** Against a temporary folder: added, changed, unchanged and removed stubs; a second
   run reports nothing; an empty catalogue and an `ERROR:` answer leave the folder untouched.
6. **Fetch over MCP.** Against a local `node:http` server answering `initialize` and `tools/call`, both
   as JSON and as an SSE stream: session header carried, dev-mode header and bearer token sent, `ERROR:`
   bodies and HTTP errors reported without the token.
7. **Generate the stubs** from the live server's answers, commit them, run it a second time to show an
   empty diff, and run `claude plugin validate --strict plugins/yvoke` on the result.
8. Spec, README, AGENTS.md row, CI step, plan entry; then `finish-task`.

## Risks

- **Descriptions are public.** The repo is public (D-02), and the stubs carry the server's descriptions,
  which D-04 accepted. Today's `oim-customers` description names two real environments
  (`iC Consult 1IM HQ environment`, `iC Consult Group IDM`) and `oim-field-qa` an internal Teams channel.
  D-22 (below) keeps the served text; the generator commits what it is given, and every scheduled update arrives
  as a pull request someone reads (P1-05).
- **Chat or Cowork may refuse `disable-model-invocation`, or honour it.** If claude.ai refuses unknown
  frontmatter, the stubs do not load there; if it honours the field, Chat may not let the user start them
  either. Both are found by P0-08 before P8-01 is ticked. Fallback then: generate without the field and
  have P1-08's `skill.prompt` hook alone answer in Yvoke sessions, accepting the listing in coding sessions.
- **The stub names a system prompt that is later renamed.** The stub then fails until the next sync; the
  failure is the server's `ERROR:` line, which the stub tells Claude to report. Not worked around: resolving
  at answer time would need Claude to apply the P1-07 rule itself, which is less reliable than baking it in.
- **Alternatives rejected.** MCP `prompts/list` with `_meta`: no area, and a second reading of the same
  catalogue that can drift from the tools. The official MCP SDK: a runtime dependency for two calls.
  Copied playbook text: ruled out by D-02 and D-04. A flag to include prototypes: nobody needs it yet.
